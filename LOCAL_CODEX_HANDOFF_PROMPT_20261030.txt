3. 연구 가설과 네 모델
======================================================================

모든 비교의 학습 알고리즘은 FastSAC이다.
  biHAM: BilateralMAGNet, 구조적 좌우 대칭, augmentation OFF.
  sym_aug_HAM: HAMNet/MultiRange, augmentation ON.
  HAM: HAMNet/MultiRange, augmentation OFF.
  MLP: Holosoma native FastSAC MLP, augmentation OFF.

원하는 가설:
  같은 오른쪽 command holdout에서 biHAM이 왼쪽 학습을 오른쪽 추종으로 연결해
  일반 HAM/MLP보다 좋은 미학습 방향 일반화를 줄 것인가?
  sym-aug HAM은 반사 합성 학습을 사용하는 비교 조건이다.

기존 v2에서는 MLP도 오른쪽을 잘했고 일부 오른쪽 지표가 biHAM보다 좋았다.
biHAM은 학습한 왼쪽도 추종 오차가 컸다.
'biHAM만 성공하고 MLP는 거의 반드시 즉시 넘어져야 한다'는 전제는 성립하지 않는다.
MLP가 미학습 명령에 외삽하는 것은 가능하지만 보장되지는 않는다.

우선 감사할 내용:
  1) 물리 command vy<0 유입 여부.
  2) augmentation으로 합성된 오른쪽 명령을 학습했는지.
  3) normalization/phase가 vanilla 조건을 바꿨는지.
  4) 오른쪽 명령을 바꿨을 때 실제 속도도 바뀌는지, 단순 drift인지.
  5) 학습한 왼쪽 성능과 미학습 오른쪽 성능의 차이.
  6) yaw/외란/초기 속도/탐색의 실제 움직임과 명령 유입의 구분.

가능한 설명이지만 미확인인 것:
  목표 vy=0인데 몸이 왼쪽으로 흐르면 오른쪽 보정을 배울 수 있다.
  MLP가 목표속도-현재속도에 따른 제어 관계를 익혀 음수 목표까지 외삽할 수 있다.
  이 설명이 실제 run의 원인임을 실험으로 입증한 것은 아니다.
  같은 초기 상태에서 vy=0/-0.3/-0.6만 바꾸는 평가 등으로 확인할 여지는 있다.
  추가 연구를 이미 수행했다고 말하거나, 새 학습을 임의로 실행하지 마라.

현재 30k의 질문:
  'domi phase/반사 정규화 없이 기본 Holosoma MLP도 오른쪽을 따라가는가?'
이는 정규화 하나만 바꾼 엄밀한 A/B가 아니다.
v2와 phase, IsaacGym→IsaacSim, compile, 학습 길이10k→30k도 달라졌다.
결과 차이를 정규화 하나의 인과 효과로 결론 내리면 안 된다.


======================================================================
4. 명령 제한의 정확한 구현
======================================================================

현재 '왼쪽만'은 오른쪽 제외(no-right)라는 의미로 사용 중이다.
선속도는 앞/뒤/왼쪽 세 방향이며 왼쪽 횡이동만 있는 것은 아니다.
  body +vx=전진 / -vx=후진.
  body +vy=왼쪽 / -vy=오른쪽.
  +yaw=반시계 회전 / -yaw=시계 회전.

파일:
  src/holosoma/holosoma/managers/command/terms/three_direction.py
함수:
  ThreeDirectionCommand._resample(env_ids)

실제 핵심:
  super()._resample(env_ids)
  speeds = self.commands[env_ids, :2].abs()
  direction = torch.randint(3, (env_ids.numel(),), device=self.env.device)
  self.commands[env_ids, 0] = torch.where(
      direction == 0, speeds[:, 0],
      torch.where(direction == 1, -speeds[:, 0], 0.0))
  self.commands[env_ids, 1] = torch.where(direction == 2, speeds[:, 1], 0.0)

부모는 vx/vy/yaw와 standing 처리를 샘플링한다.
subclass가 반환 전에 최종 vx/vy를 덮어쓰고 yaw는 그대로 둔다.
부모가 잠깐 만든 음수 vy는 최종 actor 입력 명령이 아니다.
YAML의 lin_vel_y=[-1,1]만 보고 오른쪽을 학습했다고 결론 내리지 마라.

재샘플링 사건 기준 이론 비율:
  정지20%.
  이동80%를 앞/뒤/왼쪽 각1/3로 분배: 전체 중 각 약26.67%.
  오른쪽0%.
속력 범위는 기본 샘플의 절댓값이므로 0~1m/s.
이동 yaw는 [-1,1] rad/s이며 정지로 선택되면 vx/vy/yaw 모두0이다.
명령 재샘플링 시간은 기본10초다.
실제 정책 입력의 누적 방향 비율은 명령 유지시간/리셋/episode 길이에 의해 달라질 수 있다.

생명주기:
  managers/command/terms/locomotion.py:
    LocomotionCommand.setup/reset/step/_resample
  managers/command/manager.py:
    CommandManager._register_class_term 등
setup에서 만든 subclass instance를 reset/step에서도 재사용한다.
reset/step config에 부모 클래스 경로가 보인다고 sampler가 부모로 교체되는 것이 아니다.
CPU 검사에서 reset과 주기적 resample 모두 no-right임을 확인했다.

문자 그대로 왼쪽 횡이동만 주는 선택지도 준비돼 있다.
  --command-mode left-only
  exp:g1-29dof-mlp-left-only-vanilla-fast-sac-30k
  native sampler, vx=[0,0], vy=[0,1], yaw=[-1,1], standing20%.
현재 GPU2 run은 이 옵션이 아니라 기본 no-right다.

중요한 구분:
  오른쪽 목표 명령 미경험 != 실제 오른쪽 움직임 미경험.
SAC 탐색, 균형 회복, 관성, push, 초기 속도 등으로 actual body vy<0은 가능하다.
yaw에 의해 world-frame 방향이 달라지는 것도 body vy 목표 부호와 별개다.
실제 신체가 절대로 오른쪽으로 가지 못하도록 하려면 상태 제약/환경 개입이 필요하고,
이는 현재 command holdout과 다른 MDP 실험이다.

sym-aug HAM은 환경 sampler가 no-right여도 반사된 오른쪽 명령과 액션을
합성 학습하므로 일반 MLP/biHAM의 command holdout과 정보 노출이 다르다.

설정 계열은 IsaacSim5.1.0 / IsaacLab2.3.2.
실제 torch 세부 버전은 필요하면 활성화 후 확인하라. 추정해서 쓰지 마라.
Python 경로만 직접 부르면 PATH/PYTHONPATH/LD_LIBRARY_PATH가 빠질 수 있다.

패키지 선언 requires-python은 src/holosoma/pyproject.toml의 >=3.10이다.

서버 hssim에 연구 의존성 opt_einsum3.4.0/icecream2.2.0을 설치했던 기록이 있고,
pyproject에는 opt-einsum>=3.3.0, icecream>=2.1.3을 추가했다.
이들은 네트워크 이식 지원 의존성이지 보상/정책 학습 규칙 변경이 아니다.

8. FastSAC 네트워크 연결 방식과 보존한 부분
======================================================================

기본 native 경로:
  agents/fast_sac/fast_sac_agent.py : FastSACAgent.
  agents/fast_sac/fast_sac.py : Actor, Critic, DistributionalQNetwork.
  agents/fast_sac/fast_sac_utils.py : replay/정규화/checkpoint 지원.

현재 MLP의 Actor:
  입력 → Linear512 → LayerNorm → SiLU
       → Linear256 → LayerNorm → SiLU
       → Linear128 → LayerNorm → SiLU
       → mean/log_std heads.
  native head의 초기값은0.
Critic hidden width는768, 독립 Q 2개, categorical atoms101.
지원 범위 v_min=-20, v_max=20.
SAC의 tanh, action scaling/bias, log_std bounds, Gaussian sampling,
entropy/alpha, reward, categorical projection 등은 native 경로를 유지한다.
Actor.forward는 deterministic mean action을 반환하고 explore는 학습 시 샘플링한다.

biHAM preset은 _target_을 BilateralFastSAC로 바꾸고,
기본 Actor/Critic의 feature 구현을 BilateralMAGNet bank로 감싼다.
  fast_sac_adapter.py:
    BilateralBank / ActorFeatures / BilateralSACActor.
    BilateralQ / BilateralSACCritic / build_bilateral_sac.
  bilateral_fast_sac.py:
    BilateralFastSAC.setup, shared router optimizer 및 update 관리.

biHAM 기본 구조:
  subnet hidden=(192,384,192).
  router hidden=(256,256,128).
  num_module=4 / gate_sizes=8.
  share_ab_modules=False / use_sym_param=True.
  feature_bias_scale=.5 / compose_mode=feature.
  checkpoint_layers=True / use_fast=False.
  weight_recenter=False.
원본 YAML의 weight_recenter=True와 달리, 이식에서는 추가 갱신을 피하려고 False다.
이 차이를 숨기거나 원본 학습 전체를 재현했다고 말하지 마라.

Actor와 online Q 두 bank는 router를 공유한다.
Actor 전용 파라미터, Q 전용 파라미터, router 파라미터의 optimizer를 분리한다.
공유 router를 actor_optimizer와 q_optimizer 양쪽에서 중복 step하지 않는다.
gradient를 모아 _finish_update에서 router를 한 번 갱신한다.
target Q/router는 deepcopy로 분리된다.
actor update 시 Q parameter를 temporarily freeze하여 입력 action gradient는 유지한다.
과거 Torch2.4 functional_call이 shared router alias를 교체하는 문제를 피한 구현이다.

Critic은 privileged critic observation에 actor observation의 router context를 붙인다.
candidate physical action을 side action view로 변환하여 Q에 사용한다.
biHAM Q는 좌우 categorical logits를 평균한다.

HAM:
  ham_adapter.py / ham_fast_sac.py.
  원본 MultiRange/HAM executor와 full left/right concat 입력을 사용.
  hidden=(384,576,384), use_sym_param=False, checkpoint_layers=False.
  네트워크에 biHAM의 좌우 parameter tying을 강제로 적용하지 않는다.
  공유 router 갱신 방식은 같은 계열을 사용한다.
  HAM Q 출력은 native categorical projection과 맞게 float32로 취급한다.

9. 좌우 IO와 물리 action mapping의 한계
======================================================================

adapter.py의 BilateralPolicy/ObservationView가 ObservationManager layout에서
이름 기반으로 관측을 나누고 joint indices/signs를 구성한다.

로봇 joint 순서를 추정하거나 하드코딩한 숫자로 무작정 맞추지 마라.

한쪽 side output:
  waist3 + own leg6 + own arm7 =16.
좌우 합계32를 Holosoma의 물리29 action으로 매핑한다.
팔다리는 해당 side, shared waist는 물리 좌표로 변환한 양쪽 값을 평균한다.
원본 joint resolver와 mirror sign을 사용한다.
SAC의 실제 action scale/distribution은 Holosoma 방식이다.

중요한 불일치:
  원본 domi의 pre-merge side action history는32차원이다.
  Holosoma last_action은 merge된 physical29차원이다.
  waist를 복제해 side view를 구성할 수 있지만 원래 독립 waist 두 출력은 복원할 수 없다.
hidden history나 action space를 임의로 추가해 이 문제를 숨기지 않았다.
또한 domi absolute joint position과 Holosoma default-relative joint position은
관측 의미 차이가 남아 있다. 기본적으로 Holosoma 의미를 유지했다.
원본 연구 MDP 전체와 동일하다는 주장은 금지한다.

10. 세 가지 정규화 선택과 ReflectionNormalization의 정확한 원리
======================================================================

혼동하지 말아야 할 세 가지:
  EmpiricalNormalization: 기본 관측 정규화.
  ReflectionNormalization: 여기서 추가한 반사 호환 관측 정규화.
  LayerNorm: 네트워크 hidden layer 내부 정규화. 위 두 가지와 별개다.

기본 EmpiricalNormalization:
  agents/fast_sac/fast_sac_utils.py
  forward(x) = (x - mean) / (std + eps).
  기본 eps=1e-2.
  학습 중 각 채널의 running mean/variance를 갱신한다.
  eval에서 저장된 mean/std를 사용하고 update=False로 고정한다.

물리 command vy와 normalized_vy의 부호는 다른 의미다.
예: 평균0.3, 표준편차0.2라면(설명용, eps 생략):
  실제 +0.6 → normalized +1.5
  실제  0.0 → normalized -1.5
  실제 -0.6 → normalized -4.5
정규화된 음수는 '평균보다 작다'는 뜻이다.
'MLP가 음수 숫자를 전혀 못 봤다'는 말은 부정확하다.
정확한 가설은 '물리적인 vy<0 목표 명령을 받지 않았다'다.

현재 run의 실제 CSV 예:
  step13 / env0 / raw vy=0 / manager_vy=0 / normalized_vy≈-0.46494594.
이는 정상적인 기존 empirical 정규화이며 오른쪽 목표 명령 유입의 증거가 아니다.
오른쪽 유입 여부는 정규화 전 physical command를 검사하는 감사 카운터로 판단하라.
actual body_vy가 음수인 것 역시 목표 command 부호와 별개다.

반사 정규화의 목표:
  M=좌우 반사, N=정규화라고 할 때 N(Mx)=M(Nx)를 만족시키는 것.
부호 반전 odd 채널의 평균을0으로 만들고,
좌우 교환 채널의 평균/분산을 해당 mirror sign/permutation에 맞춰 묶는다.
이것이 biHAM 네트워크 앞단의 전처리가 구조적 equivariance를 깨지 않게 한다.

파일:
  agents/modules/bilateral/normalization.py
클래스:
  ReflectionNormalization(EmpiricalNormalization)
  DomiSymmetry(SymmetryUtils)

ReflectionNormalization.update(x) 실제 순서:
  1) super().update(x)로 Holosoma 기본 통계 갱신.
  2) reflected_mean = mean[:, mirror_indices] * mirror_signs.
  3) new_mean = 0.5*(mean + reflected_mean).
  4) new_var = 0.5*(var + var[:, mirror_indices])
               + 0.25*(mean - reflected_mean)^2.
  5) mean/var/std 버퍼를 갱신한다.
분산은 부호를 곱하지 않고 인덱스만 교환한다.
constructor는 실제 mirror 함수를 이용해 permutation/sign을 추출하고 involution을 검사한다.

vy처럼 자기 자신이 부호 반전되는 채널:
  new_mean=0.
  new_var=old_var+old_mean^2.
예: 보정 직전 평균0.3/표준편차0.2라면 보정 후 평균0,
표준편차sqrt(0.04+0.09)≈0.3606이다.
이 예는 특정 실제 run 통계가 아니라 수식 설명이다.

반사 정규화는 오른쪽 transition을 replay에 추가하지 않는다.
MLP의 출력 자체를 좌우 대칭으로 강제하지도 않는다.
MLP는 입력 좌표 변환을 첫 affine layer에서 흡수할 수 있으므로 표현력보다
최적화/implicit bias/수치 조건이 달라지는 문제다.
정규화가 일반화에 영향을 줄 가능성은 있지만 MLP에서 어느 쪽이 낫다는 결과는 없다.
biHAM에서는 정책의 좌우 대칭을 전처리까지 보존하는 구조적 근거가 강하다.
이 두 판단을 혼동하거나 MLP가 잘한 원인을 반사 정규화로 확정하지 마라.

11. domi 원본은 관측 정규화를 어떻게 하는가
======================================================================

2026-10-30 서버 domi 원본을 직접 읽어 확인한 내용이다.
원본에 이 저장소의 ReflectionNormalization 파일이 그대로 있는 것은 아니다.

domi 원본:
  source/domi/src/domi/rl/normalize.py
    NormalizeObservation: 약35행부터.
    TensorDict 항목별 RunningMeanStd로 정규화.
    기본 eps=1e-6.
    TensorDict 경로는 (x-mean)/sqrt(var+eps)를 사용한다.
  source/domi/src/domi/rl/running_mean_std.py
    RunningMeanStd / update_from_moments.
  source/standalone/workflows/imm/train_ma_v2.py
    SHARE=True 선언: 약193행.
    좌우 observation normalizer 공유: 약2385~2398행.
  source/.../g1_art/config/loco_env_cfg.py
    _mirror_vel_cmd: vy와 yaw 부호 반전.
    make_obs_cfg(...,mirror=True): 관측에 mirror modifier 적용.
    약2956~2957행:
      left  = make_obs_cfg('left', False, ...)
      right = make_obs_cfg('right', True, ...)

원본 학습 경로에서는 좌우 canonical view를 먼저 만들고 정규화한다.
  physical state
    → left view / mirrored right view
    → 공유된 RunningMeanStd로 정규화
    → 네트워크

통계 공유 실제 핵심:
  obs_rms[k_dst] = obs_rms[k_src]
같은 값을 복사하는 것이 아니라 같은 RMS 객체를 참조하게 한다.
예를 들어 실제 vy 목표가+0.5이면 한 view의 command는+0.5,
반사된 다른 view의 command는-0.5이며 두 표현이 공유 통계에 기여한다.
이는 물리 환경에 오른쪽 목표를 내보냈다는 뜻은 아니다.

여기 Holosoma의 경로:
  physical observation
    → EmpiricalNormalization 기본 갱신
    → 평균/분산을 수식으로 반사 대칭 projection
    → 정규화된 observation
    → 필요하면 biHAM/HAM adapter의 side view
MLP에서는 adapter 없이 정규화된 기존 관측이 native MLP로 들어간다.

목표는 비슷하지만 수집 단위/갱신 수식/eps/IO 구조가 다르다.
domi의 공유 RMS를 통째로 복사한 것도 아니고,
두 전체 파이프라인의 통계/학습 동등성을 검증한 것도 아니다.
중간 관측 잡음, count 처리, 업데이트 순서까지 완전히 같다고 주장하지 마라.
이 설계 차이는 현재 연구의 중요한 감사 항목이다.

======================================================================
12. 이미 확인한 기본 분산 갱신 오류와 기타 미확인 지점
======================================================================

별도의 확인된 문제:
  agents/fast_sac/fast_sac_utils.py
  EmpiricalNormalization.update()

현재 기본 코드는 mean을 갱신한 후:
  delta2 = batch_mean - updated_mean
  M2 = old_var*old_count + batch_var*batch_count
       + delta2^2 * old_count*batch_count/new_count
를 사용한다.
올바른 분산 병합 correction은 갱신 전 평균 차이:
  delta = batch_mean - old_mean
의 delta^2를 써야 한다.

실제 CPU 예:
  먼저 [0,0], 다음 [2,2]를 update하면 전체 평균1/분산1이어야 한다.
  기존 코드에서 평균1/분산0.25가 나오는 것을 확인했다.
Git의 공식 기반 commit b739a6c에도 같은 수식이 있었음을 확인했다.
이 오류를 연구 네트워크 이식에서 새로 만든 것이라고 설명하지 마라.
ReflectionNormalization도 부모 update를 먼저 호출하므로 이 오류를 상속한다.
domi RunningMeanStd.update_from_moments는 갱신 전 delta^2를 사용한다.

현재 30k baseline에서는 사용자 요구대로 기존 Holosoma 정규화를 유지하기 위해
이 부모 수식을 수정하지 않았다.
이것은 기존 구현과 동일한 기준을 확보하려는 선택이다.
오류의 모델별 성능 영향이나 오른쪽 순위에 대한 인과 효과는 입증하지 않았다.
수정본은 새 preset/version/출력으로 분리하고, 현재 run에 소급 혼합하지 마라.
로컬 Codex가 이를 발견했다고 바로 실행 중인 서버 코드를 hot-fix하지 마라.

그 외 코드에서 볼 수 있으나 이 대화에서 원인으로 확정하지 않은 검토 지점:
  FastSACAgent.get_example_obs()는 ONNX export용으로 env.reset_all()을 호출한다.
  학습 loop의 local obs가 export 뒤 새 env 상태와 일치하는지 추가 감사할 여지가 있다.
  이것을 오른쪽 command leakage로 확정하지 마라.
  현재 native 동작을 바꾸거나 기존 결과를 무효라고 선언한 상태가 아니다.

과거 수정한 문제와 현재 남은 문제를 혼동하지 마라.
v2에서 수정한 정규화-반사 비호환 문제와 위 분산 병합 오류는 서로 다른 문제다.
'정규화 문제 해결한 v2'라는 말은 모든 정규화 문제가 사라졌다는 뜻이 아니다.

13. 기본 phase와 domi phase의 실제 차이
======================================================================

기본 구현:
  managers/command/terms/locomotion.py : LocomotionGait.
  managers/observation/terms/locomotion.py : sin_phase, cos_phase.
  config_values/loco/g1/command.py : gait_period=1.0, randomization_width=.2.

기본 LocomotionGait는 left/right 두 phase 버퍼를 관리한다.
두 다리는 반 주기 차이다.
실제 관측은 sin(각 다리 phase), cos(각 다리 phase)로 총4채널이다.
이동 중 sin=[s,-s], cos=[c,-c] 구조다.

domi 구현:
  managers/command/terms/domi_gait.py : DomiGait, sin_phase, cos_phase.
  agents/modules/bilateral/original/phase_clock.py : DomiPhaseClock.
원본 단일 clock의 [sin(2πphase),cos(2πphase)]를 각 다리 표현으로 bridge한다.
이동 중 관측의 좌우 부호 구조는 기본 Holosoma와 같다.
'domi로 바꿔야 처음으로 대칭 phase가 생긴다'고 말하지 마라.

달라진 점:
  [학습 중 샘플링]
    기본: 주파수 U[0.8,1.2]Hz. 주기가 U[0.8,1.2]초인 것이 아니다.
    domi: 주기 U[0.9,1.1]초.
  [명령 재샘플링]
    기본: 주파수 변경.
    domi: 주기와 시작 phase offset 변경.
  [정지 입력]
    기본: phase가 양발 π여서 sin≈[0,0], cos=[-1,-1].
    domi: phase_zero_stand 인코딩으로 sin/cos 모두0.
  [평가 모드]
    기본 term: 주파수1Hz 및 시작 phase 고정.
    domi term: 별도 평가 고정 분기 없이 주기/offset을 랜덤 샘플링하는 구현.
    평가 script가 무엇을 reset/복원하는지도 함께 확인할 것.
  [접촉 리셋]
    이식한 DomiPhaseClock는 contact_phase_reset=False만 지원.

phase는 보행 박자/발 역할을 나타낸다.
명령 vy가 양수인지 음수인지와 독립적으로 좌우 대칭에 관련된다.
좌우를 반사하면 지지발/스윙발도 서로 바뀌어야 한다.
교대 보행에서는 φ→φ+π이고 sin/cos 모두 부호 반전이 된다.
기본처럼 다리별 채널을 쓰면 좌우 채널 swap으로 표현할 수 있다.
현재 root augmentation_utils.py의 기본 phase 반사는 두 다리 채널 교환이다.
DomiSymmetry는 domi 인코딩에 맞게 sin/cos 전체 부호를 반전한다.
과거 archived 코드의 첫 채널만 반전하던 문제를 현재 root와 혼동하지 마라.

단순 표기만 바뀐 것이 아니라 보행 속도 분포/정지 관측/초기화가 달라진다.
MLP 자체가 domi phase를 필요로 하는 것은 아니다.
기본 phase도 일관된 반사 규칙을 쓰면 대칭 설계가 가능하다.
현재 vanilla 30k는 기본 phase를 유지한다.

14. normalization/phase/symmetry/compile 스위치
======================================================================

실제 정규화 선택:
  obs_normalization=False → nn.Identity (정규화 없음).
  obs_normalization=True, symmetry_compatible_io=False → 기존 EmpiricalNormalization.
  obs_normalization=True, symmetry_compatible_io=True → ReflectionNormalization.

CLI 예:
  --algo.config.obs-normalization True
  --algo.config.symmetry-compatible-io False

결정 위치:
  agents/fast_sac/fast_sac_agent.py : FastSACAgent.setup().
  먼저 기존 normalizer 또는 Identity 생성.
  symmetry_compatible_io=True 분기에서 DomiSymmetry를 만들고
  Actor/Critic normalizer를 ReflectionNormalization으로 교체한다.

현재 완전히 독립된 normalization_mode 단일 enum은 없다.
symmetry_compatible_io는 정규화 선택과 phase 반사 유틸 선택을 겸한다.
이를 False로 바꿔도 preset에서 이미 설정된 DomiGait/관측 함수는 원복되지 않는다.

phase 구현은 별도 class/function으로 분리돼 있으나 독립 CLI toggle은 없다.
config_values/loco/g1/experiment.py 의 _corrected_io(experiment)가:
  1) locomotion_gait setup을 DomiGait로 교체.
  2) 각 observation group의 sin_phase/cos_phase 함수를 domi 함수로 교체.
  3) symmetry_compatible_io=True 지정.
세 가지를 한꺼번에 수행한다.
따라서 phase와 normalization을 완전히 독립적으로 ablation하는 캡슐화는 미완성이다.
새로운 독립 스위치가 필요하면 기존 preset 해석을 보존하는 방식으로 구현하고 검증하라.
이미 구현돼 있다고 말하지 마라.

use_symmetry는 replay sample augmentation ON/OFF다.
구조적 biHAM 대칭, 반사 정규화, phase 선택과 다른 옵션이다.
sym-aug HAM만 True이며 현재 MLP는 False다.

compile:
  True: 정책/SAC update/정규화 forward를 torch.compile로 실행 최적화.
  False: 일반 eager PyTorch 실행.
네트워크 종류나 좌우 대칭을 켜는 옵션이 아니다.
AMP/BF16도 별도 옵션이다. compile=False라고 자동 FP32가 되지 않는다.
기존 v2의 네 모델은 당시 커스텀 compile/BF16 호환 문제 때문에 False로 통일했다.
현재 native MLP 30k는 기본 True를 유지했고 실제 GPU2에서 학습이 진행됐다.
root는 최신 compile_mode/compile_options/CUDA graph 지원을 보존한다.

17. 평가 정의와 산출물
======================================================================

scripts/evaluate_command_holdout.py:

scripts/holdout_terrain.py:
  flat nominal 평가 지면과 env origin 간격.
scripts/plot_holdout_evaluation.py:

현재 새 실험:

  case마다32trial, checkpoint마다544rollout.
  30checkpoint면 총16,320rollout 예정.
  seed20261029, 20초 rollout, 처음2초 warmup 제외.

대각선의 전체 속력 norm이0.3/0.6이다. 각 축에0.3/0.6을 주는 것이 아니다.
순수 오른쪽은 vx=0, vy=-0.3/-0.6이고 좌측은 양수 대응값이다.

각 trial의 primary metric:
  planar RMSE = sqrt(mean((vx-target_vx)^2 + (vy-target_vy)^2)).
그 trial RMSE들을 평균해 mean_linear_rmse를 만든다.
per-axis vx/vy RMSE와 yaw RMSE도 별도 기록한다.
warmup 이후 실제 관측된 첫 episode만 집계한다.
자동 reset 이전 velocity/termination을 capture하며 reset 이후 데이터를 섞지 않는다.
실패 전에 짧게 관측된 조건부 RMSE가 낮을 수 있으므로 failure/survival/
measured_steps를 함께 보고한다. 생존하지 못한 모델을 낮은 RMSE만으로 칭찬하지 마라.
초기 root/DOF/actor obs, 평균 실제 속도, 시간 곡선도 저장한다.

산출:
  evaluation/manifest.json
  evaluation/summary.csv 및 summary.json
  evaluation/right_rmse_by_checkpoint.csv 및 .json
  evaluation/videos/MLP/model_0030000/<case>/metrics.json
  evaluation/plots/tracking_rmse.png, lateral_rmse.png, survival_duration.png
  evaluation/plots/velocity_curves_*.png
videos/라는 폴더명이어도 숫자 metrics만 있을 수 있다. 모든 영상 sweep을 돌리지 않는다.

19. 로컬 개발 → push → 서버 pull → 학습/평가
======================================================================

1) 로컬에서 exp-g1-training과 기준 commit/필수 연구 파일을 확인한다.
2) 관련 소스만 읽고 요청한 기능을 수정한다. 오래된 숨은 checkout은 건드리지 않는다.
3) 기본값/기존 preset/완료된 결과를 보존한다.
4) 가능하면 CPU 검사, CLI dry-run, git diff --check를 수행한다.
5) 실험 조건 변경이면 새 preset/version/output으로 분리하고 변경 항목을 보고한다.
6) 로컬에서 관련 파일만 commit하고 기존 연구 remote/branch로 push한다.
   사용자 작업을 섞어 git add -A/강제 push/reset하지 마라.
7) 서버에서 현재 학습과 후속 평가가 모두 끝났는지 확인한다.
   실행 중 서버 pull은 뒤에 생성되는 평가 worker의 코드를 바꿀 수 있으므로 피한다.
8) 서버 root의 사용자 변경을 확인하고 clean/충돌 없는 상태에서:
     git pull --ff-only origin exp-g1-training
   이후 hssim 활성화, 새 코드/CLI CPU 검사, 지정GPU에서 새 요청만 실행한다.
9) source commit/hash, 실제 CLI, 전체 YAML, terminal log와 새 결과 폴더를 남긴다.

현재 .isaacgym gitlink 내부 dirty 상태는 강제로 지우지 마라.

기존 연결 정보를 확인하고 임의의 새 Git remote나 브랜치 구조를 만들지 마라.
checkpoint/이벤트/대형 로그는 Git 코드 push에 넣지 않고 필요한 파일만 따로 복사한다.

이 절은 앞쪽의 '23000step 학습 중' 스냅샷보다 최신이다.

학습30k는 정상 완료됐다. 1k~30k 총30개 .pt를 확인했다.
감사 최종값:
  status=complete / last_step=30000.
  policy_command_samples=122,884,096.
  negative_policy_vy_count=0.
  replay_command_samples=3,930,718,208.
  negative_replay_vy_count=0.
  min_policy_vy=0.
  forward=32,581,592 / backward=32,899,116 / left=32,674,897.
  right=0 / standing=24,728,491 / other=0.
replay 수에는 중복 샘플링이 포함된다.
이 증거는 현재 run에 대한 것이며 옛 MLP run의 실측 증거로 소급하지 마라.

처음 자동 평가는 1k checkpoint에서 실패했다.
원인:
  evaluate_command_holdout.py가 IsaacSim의 RootStatesProxy를 torch.Tensor처럼
  torch.cat에 전달하거나 .detach()하려 했다.
실제 오류:
  TypeError: expected Tensor as element 0 in argument 0, but got RootStatesProxy.
학습이나 저장 모델이 실패한 것이 아니다.

평가 코드만 다음 두 줄을 수정했다.
  reset_trial:
    torch.cat((env.simulator.robot_root_states[:], env.simulator.dof_pos), -1)
  measure:
    initial_root = env.simulator.robot_root_states[:].detach().clone()
[:]는 proxy에서 xyzw Tensor를 얻는다.
raw tensor에서도 같은 동작이므로 두 경로를 지원한다.
기존 알려진 RMSE/warmup/first-failure 검사를 Tensor와 실제 RootStatesProxy 양쪽으로
CPU 실행해 통과했다. 학습은 다시 돌리지 않았다.

최종30k의 결과부터 확인하려고 run_vanilla_mlp_30k.py에 --descending을 추가했고,
--stage evaluate --descending --execute로 GPU2 평가만 재개했다.
모든30개 평가를 수행하되 이미 완료된 checkpoint는 건너뛴다.
문서 저장 직전의 실제 결과 유무는 status.json/평가 CSV를 다시 확인하라.
아직 없는 RMSE를 예전 v2 값으로 대신 보고하지 마라.

주의: 이 마지막 평가 호환성/순서 수정은 기준4f27c00 이후 서버에서 적용한 변경이다.
로컬에서4f27c00만 받으면 다음 두 파일의 최신 수정이 빠질 수 있다.
  scripts/evaluate_command_holdout.py
  scripts/run_vanilla_mlp_30k.py
서버 git diff와 이 절을 기준으로 로컬에도 반영하고 향후 commit/push로 동기화하라.
현재 학습 artifact는 그대로 보존한다.

이 파일을 읽은 로컬 Codex는 연구 의도와 소스 상태를 짧게 확인해 주고,
사용자의 다음 코딩 요청을 받아라. 인계문서를 읽었다는 이유로 새 GPU 실험을 실행하지 마라.

전체 4096env 정책 입력 122,884,096건 기준 실제 시간 점유 비율:

정책 입력 횟수 집계이며 새 커맨드를 뽑은 횟수/서로 다른 명령 개수가 아니다.
CommandRatio TensorBoard 시계열을 100 iteration 간격으로 읽어 누적 비율을 표시한다.

분포/산점도는 commands_policy.csv의 env 0 30,001행만 사용한다.
env 0은 시간적으로 상관된 표본으로 전체 환경을 대표한다고 가정하면 안 된다.
raw vy<0은 0건. 실제 normalized_vy<0은 26,907행.
이 차이를 오른쪽 명령 노출로 해석하면 안 된다.

정규화기 통계는 1k..30k 체크포인트 30개 모두의 actor/critic mean,variance,std,count.
actor 관측 차원100, command [vx,vy,yaw] 인덱스[33,34,32].
critic 관측 차원103, command 인덱스[36,37,35].
기본 native phase는 두 발의 sin/cos라서 각 term이 2차원이다.
정규화기의 replay 기반 누적 running statistics와 env0의 단순 표본 통계를 구별한다.
슬라이더로 고른 고정 체크포인트 통계에 raw vy를 재투영한 히스토그램과
학습 당시 기록된 evolving-statistics normalized_vy 히스토그램도 구별한다.
